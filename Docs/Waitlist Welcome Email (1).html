A welcome email for everyone who joins the waitlist

When someone fills the "Join the waitlist" pop-up, they should get a fun, on-brand email from us within seconds, sent through the same Amazon SES account that already sends the app's login OTPs. This page covers how it works, what it looks like, what could go wrong, and what we need from you before writing the plan.

Brainstorm, not final Next step: plan, then Antigravity execution prompt
My recommendation in one breath
  • Add a small backend: API Gateway and one Lambda function. The site is a static export, so it can't send email by itself, and the AWS keys must never sit in the browser.
  • Keep marketing apart from OTPs: a separate SES configuration set, sender address and (ideally) subdomain, so a spam complaint on a marketing email can never slow down someone's login code.
  • Use SES's built-in contact list so every email gets a working one-click unsubscribe, which Gmail and Yahoo now require.
  • Welcome email: the "Waitlist pass" design (chosen 8 Oct). Keep the "Founder note" style for later updates.
  • Add bot protection (Cloudflare Turnstile plus rate limits) before going live, or strangers can use our form to spam other people's inboxes.
How it works

From "Join the waitlist" to their inbox

Five hops, all inside AWS except the browser. The whole thing should take under two seconds.

01 · BROWSER User submits the pop-up Name, email, phone and a Turnstile token are POSTed as JSON. WaitlistForm.tsx
02 · EDGE API Gateway receives it CORS limited to unifolio.in. Throttled so one IP can't hammer it. HTTP API · POST /waitlist
03 · LOGIC Lambda checks and saves Verifies the captcha, validates input, saves the signup once. A repeat email is not re-sent. Lambda (Node 22) · DynamoDB
04 · SEND SES sends the welcome Stored template, personalised with their name and waitlist number. Unsubscribe link added automatically. SESv2 SendEmail · contact list
05 · AFTER We watch what happens Bounces and complaints are logged and the address is suppressed so we never email it again. Config set → SNS / CloudWatch

Protecting the OTPs

Marketing and login emails must not share a reputation

Gmail and Outlook judge senders by domain and by how people react. Marketing emails get ignored and reported as spam far more than OTPs do. If both go out under the same identity, a bad week of marketing can push login codes into spam, and users can't sign in.

PieceOTP emails (today)Waitlist / marketing (new)
Sender addresse.g. no-reply@unifolio.inhello@updates.unifolio.in or hello@unifolio.in (decision below)
SES configuration setExisting, or noneNew unifolio-marketing with its own bounce/complaint tracking
UnsubscribeNot needed (transactional)Required. SES contact list unifolio-marketing adds the link and List-Unsubscribe headers
DNS recordsAlready verified: DKIM, probably SPFDKIM for the new subdomain, custom MAIL FROM, and a DMARC record on the root domain
Reply-toNoneA real inbox someone reads, e.g. founders@unifolio.in
Gmail and Yahoo bulk-sender rules (since 2024): SPF and DKIM, a DMARC record, a one-click unsubscribe header, and a spam complaint rate under 0.3%. Our volume is small, but following them from day one keeps us out of spam.
India's DPDP Act: we should collect clear consent. A line under the button such as "We'll email you about Unifolio's launch. Unsubscribe anytime." plus a link to the privacy policy does the job.
Abuse

Stopping strangers from using our form to spam people

Any form that sends an email to whatever address is typed in can be abused: a bot submits thousands of addresses that aren't theirs, those people mark us as spam, and SES pauses our whole account, OTPs included. Four layers keep that from happening.

LayerWhat it stopsWhere
Cloudflare TurnstileBots. Invisible for real users, free, no image puzzles.Widget in the pop-up, token checked in Lambda
Honeypot fieldSimple bots that fill every input.Hidden input in the form
API Gateway throttlingFloods. For example 5 requests/second overall, a burst of 10.API Gateway stage settings
Send once per addressRepeat sends to the same inbox.DynamoDB conditional write; repeats get "You're already on the list"
End to end

Setup, step by step

The order matters: DNS changes can take a few hours, so they go first. Antigravity can write all the code; the AWS console and DNS steps need someone with access.

Phase 1 · SES and DNS

You, by running scripts/ses-marketing-setup.sh with the AWS CLI · about 10 minutes plus DNS wait
  1. Confirm the SES region and production status.Use the same region the OTPs are sent from; it's already out of the sandbox there.
  2. Create the sending identity (updates.unifolio.in or reuse unifolio.in).SES gives three DKIM CNAME records to add in DNS.
  3. Set a custom MAIL FROM domain, e.g. bounce.updates.unifolio.in.One MX and one SPF TXT record. Makes SPF align for DMARC.
  4. Add DMARC on the root domain if missing: _dmarc.unifolio.in TXT "v=DMARC1; p=none; rua=mailto:dmarc@unifolio.in".Start with p=none to observe, tighten later.
  5. Create configuration set unifolio-marketing with event destinations for bounce, complaint, delivery, open and click.Send to CloudWatch for dashboards and an SNS topic for alerts.
  6. Create contact list unifolio-marketing with topic product-updates (default: opted in).This powers the unsubscribe link and page. SES allows one contact list per region, so it's named for all marketing, not just the waitlist.

Phase 2 · Backend

Antigravity writes it, you deploy · about half a day
  1. DynamoDB table unifolio-waitlist, partition key email, plus one counter item for spot numbers.On-demand billing. Stores name, phone, source page, timestamps, spot number.
  2. IAM role for the Lambda, scoped tightly.ses:SendEmail on the marketing identity and config set only, ses:CreateContact on the list, dynamodb:PutItem / UpdateItem on the one table.
  3. Lambda function waitlist-signup (Node 22, AWS SDK v3).Validate → verify Turnstile → conditional write → create SES contact → send templated email. Turnstile secret lives in SSM Parameter Store.
  4. API Gateway HTTP API with POST /waitlist.CORS allows only https://unifolio.in and www. Throttling on the stage.
  5. Bounce/complaint alerting.SNS topic emails the team if complaints spike. SES's account-level suppression list already blocks known-bad addresses.
  6. Infrastructure as code (recommended).A small AWS SAM or CDK template so the setup is repeatable and reviewable instead of hand-clicked.

Phase 3 · The email

Antigravity builds, you approve copy · about a day
  1. Write the template in MJML, compile to table-based HTML with inline styles.Kept in the repo, e.g. emails/waitlist-welcome.mjml.
  2. Write a plain-text version too.Better deliverability, and some people read email that way.
  3. Host images on CloudFront with absolute https URLs.Logo PNG at 2× size. Every image gets alt text.
  4. Upload as an SES template waitlist-welcome-v1 with {{name}}, {{spot}}, {{amazonSESUnsubscribeUrl}}.A small script in scripts/ creates or updates it.

Phase 4 · Website

Antigravity · a couple of hours
  1. Point the form at the new API via NEXT_PUBLIC_WAITLIST_API_URL, with real CORS instead of no-cors.Now the pop-up can show real errors and an "already on the list" state.
  2. Add the Turnstile widget, honeypot and consent line to WaitlistForm.tsx.
  3. Show the spot number in the success state: "You're #1,284. Check your inbox."

Phase 5 · Test and launch

Together
  1. SES mailbox simulator.success@, bounce@ and complaint@simulator.amazonses.com confirm the event pipeline without hurting reputation.
  2. Render check in Gmail (web, Android, iOS), Apple Mail, Outlook, light and dark mode.
  3. Score check with mail-tester.com, aim for 9/10 or better.
  4. Register in Google Postmaster Tools to watch domain reputation after launch.

Before the plan

Decisions to make together

Subdomain or root domain for marketing?

My pick: subdomain (updates.unifolio.in). A bit more DNS work now, much better protection for OTP deliverability later. Users still see "Unifolio" as the sender name.

Single or double opt-in?

My pick: single opt-in with Turnstile and send-once. Double opt-in ("confirm your email") is cleaner for list quality but loses 20–30% of signups, which hurts a waitlist.

Waitlist number: decided, yes

Settled by choosing the pass. Open point: start the counter at 1 or import existing webhook signups first so earlier joiners keep lower numbers. My pick: import first.

Where does "Bring a friend" go in v1?

My pick: a share link to unifolio.in with a ?ref= code stored on the signup, so referrals are counted from day one even before "skip the line" exists. Simpler alternative: link to the homepage, or replace the button with "Follow us on Instagram".

Just the welcome, or a short series?

My pick: welcome only for v1, with the contact list in place so launch announcements can go out later. Add the day-3 founder note in v2.

Where should signups live?

My pick: DynamoDB as the source of truth, optionally still forwarding to the current webhook so whoever watches that sheet isn't surprised.
